# Schema conventions

The binding ledger for Oxy Pay's PostgreSQL schema: what each decision is, and
why the obvious alternative is wrong. Read it before touching a table.

This is a **greenfield** port. Production held zero documents when it was
written, so nothing here carries a compatibility shape from Mongo; where the
Mongo model was inconsistent, this schema is not.

## Substrate

`drizzle-orm` over `postgres.js`, through `@oxyhq/db` — which owns the column
builders, the id generator, the casing authority (`DATABASE_CASING`), the
driver-error predicates, the migration ledger with its deploy-phase enforcement,
and the throwaway-database harness. Do not hand-roll anything that package
already provides; a second copy of a decision is a second copy to keep in sync.

**Extensions: NONE.** No geography, no text search, ids generated in the
application. `REQUIRED_EXTENSIONS` in `db/migrate.ts` states it as an explicit
empty list. An extension may **not** be added later by writing `CREATE EXTENSION
IF NOT EXISTS` into a migration: the duplicate-existence check short-circuits
before the privilege check, so that statement is a silent no-op where the
extension exists and a hard failure where it does not. Extensions are a database
prerequisite installed once by a privileged role.

## Ids

Every primary key is `text` holding a uuid v7, generated by the application
through `generatedId()`. The time component makes them k-sortable, so the
primary-key index stays append-mostly — which is also what lets the dashboard's
`_id`-descending keyset pagination port to `id desc` unchanged.

**`public_id` is a separate column, and the primary key is never the public
id.** Four tables carry a Stripe-parity external identifier (`merch_…`, `pi_…`,
`cs_…`, `link_…`) minted by `newId()`. The Mongo model called that field `id` on
`PaymentIntent` and `publicId` on the other three; here it is `public_id` on all
four, and `id` always means the internal key. A serializer renders `id:
row.publicId`.

**No foreign key ever points at an Oxy id.** `oxy_user_id`, `oxy_app_id`,
`sender_user_id`, `recipient_user_id` and `avatar_file_id` all belong to
another service's key space. They are enumerated in the `withoutForeignKey`
ledger in `db/__tests__/schemaGates.realdb.test.ts` with the reason, so an id
column nobody has decided about is a build failure rather than an absence.

## Closed value sets

`text` plus a CHECK derived from the SAME `const` tuple that types the column
(`schema/valueSets.ts`), never a pg `enum` — an enum puts the values in a type
whose every change is a migration and whose members cannot be removed at all.

Each tuple carries an `AssertAllListed` type alias, because `satisfies` alone
only proves each member IS a union member. The dangerous direction is the other
one: a union gaining a member no tuple lists type-checks everywhere and is then
refused by a CHECK on the first write of the new value, in production.
`schema/__tests__/valueSets.test.ts` covers what types cannot — the runtime
`PAYMENT_INTENT_STATUSES` array and the base-unit regex in another package.

### A bound parameter cannot appear in DDL

**Never interpolate a value into a `sql` template that becomes a constraint.** A
`${value}` in a drizzle `sql` template is a BOUND PARAMETER, and drizzle-kit
renders it into the migration as the literal text `$1`; a CHECK cannot carry
one, so the migration fails at apply time. `tsc` is clean and `drizzle-kit
generate` reports success, so nothing before the apply catches it. Measured
here: the first generated migration contained `CHECK (next_derivation_index >=
$1)` the moment a bound became a named constant instead of a literal typed into
the template. Use `sql.raw(...)` with the value interpolated into the STRING.
`db/__tests__/schemaGates.realdb.test.ts` fails the build on any `$<digit>` in a
migration.

## Money

`amount` is `text` holding a canonical base-unit integer string, with a CHECK
matching `isBaseUnitString`'s own pattern exactly.

Not `bigint`: postgres.js decodes `int8` as a STRING anyway, and an `int8`
ceiling is not the domain's — the application works in JS `bigint`, which is
unbounded. `text` keeps the wire representation byte-for-byte and the CHECK
supplies the validation Mongo never had. The CHECK refuses a leading zero, so
one amount has exactly one spelling.

## Counters, and why they are `integer`

A wrong derivation index is not a wrong number on a screen. It is money at an
address the recipient cannot spend from, or two payers sharing one address the
gateway can then attribute to neither. That is the standard every decision in
this section is held to.

`merchants.next_derivation_index` and `social_receive_cursors.next_derivation_index`
are `integer`, and that is the domain rather than a size guess: a non-hardened
BIP32 child index is bounded by 2^31 − 1, exactly `int4`'s ceiling.

**Verified against both derivation paths, not assumed.** `@fairco.in/core`
exports `MAX_SOCIAL_RECEIVE_INDEX = HARDENED_OFFSET - 1` and `assertValidIndex`
refuses anything above it; and `deriveIntentAddress` derives from a public-only
node — it throws on any extended key carrying a private key — on which
`@scure/bip32` cannot derive a hardened child at all (`Could not derive hardened
child key`). Both numbers are `2147483647`. `db/__tests__/derivationIndexBound.test.ts`
pins the agreement, by CROSSING the boundary rather than by comparing a constant
against itself, and fails the build if the derivable space ever widens — at
which point `integer` would silently start refusing legal indices.

Two consequences, both wanted:

- Exhausting it raises `22003` and REFUSES the reservation, instead of wrapping
  to an index already handed out — an address that already has a payment on it.
- The value comes back as a JS `number`. A `bigint` column would make it a
  string, so `index + 1` would be CONCATENATION (`"0" + 1 === "01"`) and derive a
  completely different address. Pinned by two consecutive reservations in
  `db/__tests__/derivationIndex.realdb.test.ts`; one reservation cannot tell a
  number from a string that prints the same.

## Composite foreign keys carry the invariants a CHECK cannot

A CHECK sees one row of one table. Three rules here span two tables, so they are
expressed as composite references instead:

- `payment_intents (merchant_id, network) → merchants (id, network)`. This is
  the network firewall — `createIntent`'s `NetworkMismatchError` — in the one
  form no future code path can route around. Its implicit `ON UPDATE RESTRICT`
  additionally means a merchant's network cannot change out from under an intent
  that already exists.
- `checkout_sessions` and `payment_links` each reference `merchants (id,
  oxy_app_id, environment, network)`. Those three fields are denormalized from
  the merchant at creation time; carried by the reference, they are the
  merchant's values or the row does not exist.

**The targets must be `unique()` table constraints, not `uniqueIndex()`.**
drizzle-kit emits every `ALTER TABLE … ADD CONSTRAINT … FOREIGN KEY` BEFORE every
`CREATE UNIQUE INDEX`, so a foreign key pointed at a unique INDEX fails to apply
with `42830 there is no unique constraint matching given keys` — the target does
not exist yet at that point in the file. Measured against a real server; `tsc`
and `drizzle-kit generate` are both clean either way.

## `ON DELETE`

Decided per relation, never defaulted:

- `restrict` on everything in the money graph. A merchant with payment history
  cannot be deleted, and losing the money record is never the right consequence
  of removing a party. Nothing deletes any of these today; `restrict` states what
  would happen rather than leaving it to whoever writes that statement.
- `cascade` on `webhook_deliveries.payment_intent_id` alone. A delivery log is
  derived from its intent and has no meaning without it.

## CHECK constraints that were considered and REJECTED

An empty table makes almost any constraint expressible, which is exactly why
each one has to be checked against every writer first. Three that look obvious
and are wrong:

- **`livemode ⇔ environment = 'production'`** would refuse the registration of
  every production merchant. Nothing writes `livemode`; every row carries the
  default.
- **`(webhook_url IS NULL) = (webhook_secret IS NULL)`** would refuse a
  currently-legal write. Both `POST /v1/merchants` and its PATCH accept either
  field alone; the incoherent state is reachable and already handled, by
  `routes/webhookDeliveries.ts` refusing to send when either is missing.
- **`expires_at > created_at`** compares an application clock against a database
  default and would fail on skew, for no invariant anyone depends on.

Two that ARE there, because every writer was checked:

- `payment_intents_broadcast_requires_txid_check`. `submit_tx` is the only path
  to `broadcast` and sets `txid` in the same write; `confirming` and `settled`
  are reached only by the settlement watcher, which selects on `txid` being
  present. `failed` is deliberately outside the set — `approved → failed` is
  legal and pairs with no txid.
- `webhook_deliveries_status_agrees_check`. `delivered` and `last_status` are two
  spellings of one fact and both writers derive the second from the first; the
  CHECK is that derivation, where the two cannot come apart.

## Protected columns

`db/protectedColumns.ts` withholds `merchants.webhook_secret` and
`merchants.next_derivation_index` from every ordinary read, at the TYPE level.
`xpub` and `client_secret` are deliberately NOT in the registry: both appear in
a DTO by design, so listing them would not withhold anything — it would only
make every read name them explicitly, which is the opposite of a guard.

## Timestamps

`created_at` and `updated_at` are `timestamptz` from `@oxyhq/db`, defaulted at
millisecond precision (a `timestamptz` carries microseconds and a JS `Date` does
not, which silently breaks any keyset built on one). `updated_at` is maintained
by the application through drizzle's `$onUpdate` — so it fires on `db.update()`
and on an `ON CONFLICT DO UPDATE` branch, and NOT on a raw `db.execute(sql\`update
…\`)`. `social_receive_cursors` gained both columns, which the Mongo model did
not have.

## Testing

Every database property is tested against a REAL Postgres server, one throwaway
database per test file, created and migrated through `db/migrate.ts`'s own `main`
rather than a second composition of `runMigrations`. A mocked `db.insert()`
accepts any statement, including one the server rejects — so a CHECK, a unique
index, a row lock and the driver's decoding of an `int4` have no mocked
counterpart at all.

The suites skip when `TEST_DATABASE_URL` is unset, so a developer without a
container is not blocked — and `schemaGates.realdb.test.ts` turns that skip into
a RED build when `CI` is set, because a skipped suite and a passing suite are
indistinguishable in a summary line.
